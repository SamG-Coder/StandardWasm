# StandardWasm contributor rules

- Preserve names supplied by the user. Use alternative place or project names only on request.
- Accept compiled .NET Standard libraries as input. Keep the browser runtime independent of Blazor.
- Keep metadata loading, IL translation, module emission and browser integration separate. Use descriptive names and small cohesive modules.
- Comment invariants, stack transitions, control-flow assumptions and CLR-to-Wasm semantic differences. Keep straightforward code readable through naming.
- Add an ordinary C# library case for each new compiler capability. Compare the same assembly on .NET and Wasm. Verify browser claims in a real browser.
- Diagnose unsupported operations explicitly. Never silently approximate checked arithmetic, exception handling, initialization or object lifetime.
- Use standardized WebAssembly features where they implement the required semantics. Identify engine requirements and measure performance claims.
- Keep self-hosting dependencies visible. Only mark self-hosting complete after a generated compiler recompiles itself and passes the fixtures.
- Commit source, reproducible build inputs and documentation. Exclude downloaded dependencies, generated modules and build intermediates.
## Working together

Claude and Codex are equal engineering partners. Read GOAL.md, fetch main, then check open issues, PRs and docs/decisions/. Use GitHub issues and PRs for coordination so another session can reconstruct the work.

1. Review another agent's pending milestone PR first, then unblock a dependency or claim an independent issue. Identify your role in coordination comments. Post a claim with UTC time, milestone, branch, scope, touched areas and acceptance checks. Re-read the issue after posting. The earliest valid claim takes precedence. Agree on interfaces before taking overlapping work.
2. Use one branch and worktree for an active stage or milestone. Start from current main and name the branch `codex/<issue>-<slug>` or `claude/<issue>-<slug>`. For example, run `git worktree add ../standardwasm-issue-12 -b codex/12-byte-reader origin/main`, then run `npm ci` in the new worktree. Keep committing related changes and review fixes to that branch. Use a separate worktree and branch when another agent owns an independent milestone.
3. Define what finishes the milestone on its GitHub issue before implementation. Use issue comments and commits for progress and handoffs. Apply a work-type label and the relevant `area:` label. Link related issues and record the acceptance checks. Record shared interface or architecture decisions under `docs/decisions/`. Put runnable examples under `demos/stage-NN-name/` and follow the demo index.
4. Open one PR when the stage or milestone meets its acceptance criteria and is ready for independent verification. Link the issues it completes with closing keywords. Put follow-up review fixes on the same branch and PR. Record the verification commands, results, engine versions, limitations and any remaining work. The author posts READY with the full tested head SHA. A different agent posts APPROVE or REQUEST CHANGES with that full SHA and reasons. Use role-prefixed comments when sharing a GitHub account.
   - **Focused verification per PR (owner direction, 2026-11-27).** Before READY, the author runs the fast gate: the native-compiler probe, the non-runner demo loop, and the self-compile when `src/` changed. The author also runs the affected stage demos with `npm run demo -- <stage> --no-rebuild`, which reuses the compiler from the last `npm test`, for runners that support it (stages 42, 69, 70, 74, 110 and 151) and their own repros. The reviewer runs focused checks and repros. A full `npm test` before merge is needed only for changes that broadly affect generated code or self-hosting.
   - **Milestone suites.** About every two hours, one agent runs the full `npm test` and every runner demo on main HEAD, or on the integration head, and records the SHA and results in the milestone-suite issue. A milestone runs `npm test` once and then every runner demo with `npm run demo -- <stage> --no-rebuild`. A failure is bisected across the commits since the last green milestone on that line: PRs merged into main, or commits integrated into the integration head. It is then fixed forward or reverted, before new work.
5. Merge once READY and independent APPROVE match the current head, the branch includes current main, checks pass and conflicts are resolved. Recheck immediately before merging and use an expected-head guard, e.g. `gh pr merge <number> --merge --match-head-commit <sha>`. New commits require fresh attestations. Keep main free of direct and force pushes.
6. After the merge, verify the linked completed issues are closed and cite the merge when closing any outstanding ones. Leave unfinished work on its own labeled issue. Remove the merged branch and retire its clean local worktree once active PRs and sessions no longer rely on it. Before handing off unfinished work, record the branch, head, last passing check, blocker and next action on the issue or PR. Resolve technical disagreements with a focused experiment. Bring mission, access, spending and destructive changes to the owner.
