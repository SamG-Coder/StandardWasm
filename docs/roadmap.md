# Roadmap to binary-compatible applications

This is the staged plan for [decision 0024](decisions/0024-binary-compatible-applications.md). Each step lands through issues and PRs with CLR-compared fixtures, Node and Edge runs, and an independent review, as in AGENTS.md. Steps in the same row band can proceed in parallel once their dependencies land. Each step claims demo stage numbers on its issue when it starts.

| Step | Delivers | Depends on | Acceptance |
| --- | --- | --- | --- |
| **A · Land the current stack** | Codex's portable-compiler, exception-handling and linking PRs, and the coverage audit (#85) | (none) | Decision 0004 items 3–4. The second-generation compiler passes every CLR-equivalence case in Node and Edge. |
| **B · Application loader** | Drop zone accepting apphost `.exe` + `.dll` + `.deps.json` + `.runtimeconfig.json`, single-file bundles and self-contained folders. Resolves framework references. Diagnoses NativeAOT and mixed-mode. | (none) | Unmodified `dotnet new console`, `winforms` and `blazorwasm` publish outputs, in all three publish modes, are recognized in Edge with the exact assembly list `dotnet` reports. |
| **C · Memory model decision** | Experiment and decision: Wasm GC vs linear heap vs hybrid for pointers into managed memory, pinning, `Span<T>` and `stackalloc` | A | Fixture of `fixed`, pointer arithmetic over arrays and structs, and `Span` slicing, compared with the CLR. Measured cost of each candidate. |
| **D · Event loop and threading decision** | Experiment and decision for `Application.Run`, modal loops, `Control.Invoke`, `async`/`await` and `Thread` on a non-blocking browser main thread | A | Modal `ShowDialog` inside a click handler, a nested message loop, and an `await` continuation all ordered as on Windows. |
| **E · Full IL coverage** | Generics, virtual/interface dispatch, statics and type initializers, boxing, value types, reflection metadata, delegates, unsafe code (per C), finalizers, P/Invoke redirection table | A, C | A coverage audit over the method bodies of System.Private.CoreLib, System.Windows.Forms and System.Drawing.Common reports compiled vs diagnosed per method. The diagnosed count trends to zero. |
| **F · Upstream runtime libraries** | System.Private.CoreLib and the shared framework from dotnet/runtime compiled unmodified, with native runtime services (GC, type loader, `System.Native` shims, time, file system) supplied by the browser layer | E | The CLR oracle suite runs through upstream CoreLib instead of the current bootstrap subset. |
| **G · Console applications** | Console host: stdout, stderr, stdin, exit code, environment, virtual file system | B, F | A corpus of unmodified console `.exe` drops matches `dotnet App.dll` stdout, stderr and exit code byte for byte. |
| **H · Win32 window manager** | HWND tree, message queue, `SendMessage`/`PostMessage`, focus, capture, z-order, DPI, keyboard, mouse, IME and clipboard on browser events | D, F | Message transcripts from scripted input match those recorded on Windows for the same upstream WinForms code. |
| **I · GDI and GDI+ on WebGPU** | GDI device contexts, objects, regions, fonts and text, plus the 517 `Gdip*` entry points System.Drawing.Common uses | F | Per-API pixel comparison against Windows GDI/GDI+ within stated tolerances. Text metrics comparison. |
| **J · Native common controls** | user32/comctl32 window classes (EDIT, BUTTON, LISTBOX, COMBOBOX, SysListView32, SysTreeView32, tooltips, tabs, month calendar, ImageList, progress, track bar, status) with their message contracts and themed drawing | H, I | Each class's message contract is exercised by upstream WinForms controls and compared to Windows (state, notifications, pixels). |
| **K · Upstream WinForms** | System.Windows.Forms, Primitives, Private.Windows.Core and Drawing.Common compiled unmodified on F, H, I, J. COM/OLE, clipboard, drag/drop and UI Automation mapped to ARIA. | H, I, J | An unmodified `dotnet new winforms` application with standard controls, layout, data binding and dialogs, compared with Windows for behavior, layout, events and drawing. |
| **L · Third-party control suites** | Whatever K lacks for commercial suites (DevExpress first): reflection-heavy skinning, resources, owner draw, custom painting | K | Owner-defined acceptance test: a licensed DevExpress .NET 10 application, dropped unmodified, compiled in the browser by the self-hosted compiler, compared with Windows on the same device. Binaries are never committed. |
| **M · Blazor applications** | Microsoft.AspNetCore.Components and the WebAssembly host compiled from aspnetcore assemblies. JS interop and DOM renderer shim. | B, F | Unmodified `dotnet new blazorwasm` output dropped and run, with a DOM and interaction transcript matching the same app on Microsoft's runtime. |
| **N · Performance** | In-browser compile time, IndexedDB caching keyed by MVID and compiler hash, startup and frame costs | G, K | Measured on the same device against Windows startup and paint costs, with methodology recorded (timer resolution, warm-up, percentiles). |

## Relation to existing work

- The portable compiler, oracle, self-hosting checks and review process continue unchanged. Step A is the existing backlog.
- Stages 14 onward (custom counter, textbox, control tree, profile) stay as compiler and rendering demonstrations. They are not extended as a WinForms replacement. Where they already exercise real platform behavior (input, WebGPU parity, timing methodology), that harness is reused in H, I and N.
- Decision 0004 remains the self-hosting bar. Decision 0024 adds that the compiler users run in the browser is that self-hosted compiler.
